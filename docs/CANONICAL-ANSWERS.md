# Canonical recall answers

Canonical answers are source-grounded memorization targets generated by the existing client agent. The server validates structure and observed source associations, stores immutable wording, and independently enforces access, freshness and feedback eligibility. None of those checks certifies arbitrary prose as true. Assessment and higher-level question policies are unchanged.

## Scope and words

A `question_scope` has:

- `language`: a stable language identifier.
- `parts`: ordered `{part_id, required_facts}` descriptors, one per explicit requested part. Use meaningful stable fact descriptors rather than random identifiers or question paraphrases.
- `sources`: `{kind, source_id, components}`. Chunk components are `content` and/or `condensed_summary`; a topic uses `summary`. Sources must belong to the authorized session's chunk/topic relationships.

Target `parts` are ordered `{part_id, text}` items matching the declared scope exactly. Each nonblank text has at most 40 trimmed Unicode-whitespace-delimited tokens. Punctuation, contractions, hyphenation and math/code obey the same token convention. Labels are not stored in the text. Stored wording is not normalized or regenerated for stylistic variety.

The client must keep every indispensable fact, relationship, qualification and explicitly requested reasoning in the standalone target. Extra explanation cannot rescue a false/incomplete target. Uncertainty, contradictory evidence or an infeasible budget means clarification/unavailable, not truncation or invented certainty.

## Prepare, ask, submit

1. Start or activate the ordinary teaching session through existing tools. Retrieve and teach the relevant source material.
2. Identify the actual requested parts/facts before grading any learner response.
3. Call `get_canonical_answer` with `session_id`, `question_scope`, `purpose: "preparation"` and `context_token`. Do not show preparation material to the learner. A miss provides `observation.fingerprint`; a ready result contains unchanged accepted parts.
4. On a miss, compose a target from that observed source. Ask the question without revealing it.
5. Submit the verbatim learner `response`, rubric `grading`, `question_type`, feedback and elapsed time normally, adding `question_scope` and optional `canonical_material`:
   - Candidate: `{kind: "candidate", expected_fingerprint, parts: [{part_id, text}]}`.
   - Stored reference: `{kind: "reference", revision_id}`.
   - Explicit uncertainty: `{kind: "unavailable", reason}`.

Never attach a current fingerprint to words generated from a stale observation. A changed source requires a fresh preparation/generation step. Malformed optional material cannot discard a successfully recorded valid learner attempt.

## Two attempts and explanation-first feedback

- Correct first answer: normal `recorded`, then eligible canonical feedback.
- Failed first answer: normal linked `retry`, focused feedback without the final target, then one genuinely NEW same-level question on the SAME concept/gap.
- Submit that second response under the same `session_question_id`, with exact `retry_prompt_text` and its own `question_scope`. Do not overwrite the original prompt, reset the allowance or count the retry as a separate follow-up/unaided retention event.
- Completed second answer, either outcome: eligible feedback for the actual second question. No third linked attempt. Existing roadblock/follow-up gates still apply.

The client chooses whether explanation is needed to resolve a misconception, unfamiliar prerequisite or non-obvious relationship. If needed, explain first and then present one labelled canonical answer copied exactly; otherwise show only the target. A ready `canonical_feedback` takes presentation precedence over chunk-derived `correct_answer` fallback material. For ordinary recall, a retained source block carries `material_role: "legacy_source_fallback"`; alongside a ready target it also carries `presentation: "supporting_source_only"`. Do not dump the full lesson or show two competing targets. Grading rationale is not automatically a learner-facing lesson.

This is an intentional response policy, not a guarantee that arbitrary external clients conceal raw tool traces. Teaching scripts still precede questions about their facts; preparation-only canonical targets are withheld.

## Durable identity, freshness and correction

The server derives the learner from request context and session ownership; no public caller-controlled owner exists. Identity matches language, exact ordered scope, and current source fingerprint. Similar questions or the same chunk alone are not sufficient. Current observations include revision labels and exact title/content/summary digests; reads and acceptance recheck them. Unsupported, inaccessible or unusable source material cannot produce a ready target.

Concurrent acceptance for an unchanged identity returns established wording, not the losing stylistic variant. Corrections create immutable revisions. Explicit invalidation leaves no current target and advances the head version; ordinary acceptance cannot resurrect it. Source changes form a new identity. Prior revisions and attempt associations remain historical, without grade/SRS recalculation.

`save_canonical_answer` requires `session_id`, `question_scope`, `context_token`, `operation` and `expected_fingerprint`:

- `accept`: provide complete target `parts`; existing current wording wins.
- `correct`: provide `parts`, `expected_head_version`, `expected_revision_id` (nullable after invalidation), and nonblank `correction_reason`.
- `invalidate`: provide expected head/revision and reason, but no parts.

Corrections and invalidations append transactional head-history evidence containing the reason, prior/current revision IDs and observed source snapshot. An invalidation records this evidence even though it creates no replacement answer revision.

All material operations acquire locks in the same order: owning session, source topics sorted by ID, source chunks sorted by ID, optional feedback attempt/question, then canonical identity/head. Reads hold shared locks; writes serialize the head with an exclusive lock. Source observation, current-head selection and required attempt association share one material transaction. Ordinary attempt persistence remains outside it.

A stale head/revision produces a conflict/unavailable result rather than overwriting a concurrent correction. Head versions advance even when the current revision becomes null, preventing stale correction resurrection.

## Material-only repair and history

For feedback lookup or repair, pass `purpose: "feedback"`, `session_question_id` and `attempt_number`; preparation names neither. Eligibility derives from the persisted ordinary attempt, actual captured prompt and exact scope, not from a client force-reveal flag. Reference reads must still match the current head and sources.

Repairing material through get/save tools does not call `submit_answer`, consume an attempt, change a grade or advance a chunk. Valid attempts survive optional storage/lookup/assembly errors, with explicit actionable material-unavailable feedback. Target writes themselves are atomic and fail closed.

History retains original and captured actual wording with its response and scope. Missing historical retry capture stays null/unknown, never guessed. A legacy `question` may retain the original as a reference when capture is unknown; consult `actual_question` and `question_capture` rather than treating that reference as the actual second question.
