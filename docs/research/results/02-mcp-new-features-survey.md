# MCP New Features Survey & Applicability Map — second-memory

**Research date:** 2026-07-07. **Method:** live queries against `npm`, GitHub (`gh api`), and WebFetch/WebSearch against modelcontextprotocol.io, blog.modelcontextprotocol.io, code.claude.com, developers.openai.com, canimcp.dev, and Anthropic docs. Every factual claim below carries a source and the source's own date. Anything I could not pin to a live source is marked **UNVERIFIED**.

**The one framing fact that governs every verdict below:** the ratified spec today is still **2025-11-25**. The **2026-07-28** revision is a release candidate — RC locked 2026-05-21, final publication in three weeks from today, and the TypeScript SDK's v2 (which targets it) is beta-only, published 2026-06-30/07-02. Every client I checked negotiates against 2025-06-18/2025-11-25-era capabilities today. I've labeled 2026-07-28 material as forward-looking wherever it appears — treat it as "coming soon," not current state.

## 1. Spec revision timeline, 2025-03-26 → 2026-07-28 (RC)

| Revision | Status as of 2026-07-07 | Headline changes (one line each) |
|---|---|---|
| **2025-03-26** | Ratified | OAuth 2.1 authorization framework; Streamable HTTP replaces HTTP+SSE; JSON-RPC batching added (later removed); **tool annotations** (readOnly/destructive/idempotent/openWorld hints); audio content type; `completions` capability refined. [Changelog](https://modelcontextprotocol.io/specification/2025-03-26/changelog) |
| **2025-06-18** | Ratified | JSON-RPC batching **removed**; **structured tool output** (`outputSchema`/`structuredContent`); MCP servers classified as **OAuth Resource Servers** (PRM, RFC 9728); RFC 8707 Resource Indicators required; **elicitation** added; **resource links** in tool results; `MCP-Protocol-Version` header required on HTTP. [Changelog](https://modelcontextprotocol.io/specification/2025-06-18/changelog) |
| **2025-11-25** | Ratified — **current baseline every client below negotiates against** | **Icons** for tools/resources/prompts (SEP-973); OIDC Discovery 1.0; incremental scope consent via `WWW-Authenticate` (SEP-835); **URL-mode elicitation** + reworked `ElicitResult`/`EnumSchema` (SEP-1330/1036); sampling gains `tools`/`toolChoice` (SEP-1577); **OAuth Client ID Metadata Documents** recommended (SEP-991); **experimental Tasks** for durable/polled requests (SEP-1686); SSE polling/server-initiated-disconnect support (SEP-1699). [Changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog) |
| **2026-07-28** | **Release candidate** (locked 2026-05-21; final in ~3 weeks). SDK v2 beta already implements most of it. | Largest revision since launch — see full breakdown in §4/§14. Removes protocol sessions & the `initialize` handshake (**stateless core**); new `server/discover`; **Multi-Round-Trip Requests (MRTR)** replace server-initiated `sampling/createMessage`/`elicitation/create`/`roots/list`; **Tasks move out of core into an extension**, redesigned; **SSE resumability removed outright**; `Mcp-Method`/`Mcp-Name` routing headers + `ttlMs`/`cacheScope` caching hints; JSON Schema 2020-12 fully unlocked for schemas; **Roots, Sampling, and Logging formally deprecated** (12-month window, still functional); **OAuth DCR deprecated** in favor of Client ID Metadata Documents; `iss` validation (RFC 9207); extensions framework formalized (MCP Apps, Tasks, auth extensions). [Blog: RC announcement](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/) · [Draft changelog](https://modelcontextprotocol.io/specification/draft/changelog) |

**SDK version cross-reference** (live `npm view @modelcontextprotocol/sdk`, 2026-07-07): this server pins `^1.27.1` (published 2026-02-24). Latest v1.x is **1.29.0** (2026-03-30) — no v1.x release since March despite it now being July, because SDK development has shifted to v2. **v2.0.0-beta.1** shipped 2026-06-30 targeting the 2026-07-28 spec; **beta.2** shipped 2026-07-02. v2 is a package split (`@modelcontextprotocol/server` / `client` / framework adapters replace the monolithic `sdk` package) and is described by its own release notes as passing the MCP conformance suite "except the tasks suite: tasks moved to an extension in 2026-07-28, and we aim to ship support... soon after." [v2.0.0-beta.1 release notes](https://github.com/modelcontextprotocol/typescript-sdk/releases/tag/v2.0.0-beta.1). v1.x stays supported "with bug fixes and security updates for at least 6 months after v2 ships" — i.e., no forced migration urgency yet.

## 3. Top 5 opportunities for this server

### 1. Rebuild the `instructions` payload around Claude Code's 2KB truncation + "tool search" reality
- **User-visible benefit:** Today, the ~8KB `SERVER_INSTRUCTIONS` almost certainly gets silently cut to a small fraction of itself in Claude Code (documented 2KB-per-server cap, or ~4KB shared across servers per open issue #43474) and to "first 512 characters" in ChatGPT's stated best practice. Front-loading the highest-value guidance (when to call `get_server_workflow`, when to call `start_learning`/`teach_next`, core do/don't rules) into the first ~1.5–2KB, with the rest demoted into the fallback tool, means the *part of the instructions that actually survives* is deliberately chosen rather than whatever happens to fall before the truncation point.
- **Client-support risk:** Low — this is fixing a documented, dated, currently-open problem, not betting on a speculative feature.
- **Implementation surface:** `src/shared/instructions.ts` (content restructuring), `src/server/server-workflow-tools.ts` (the `get_server_workflow` fallback — already exists, becomes the "depth" tier). Pure content/prompt-engineering change, no protocol code.

### 2. Elicitation for `delete_chunk` and other destructive confirmations (form mode only)
- **User-visible benefit:** Native, zero-config confirmation dialogs in Claude Code today ("elicitation dialogs appear automatically") instead of relying on the calling model to ask nicely before destructive orchestration tools run.
- **Client-support risk:** Medium — solid in Claude Code/Cursor/VS Code today; unverified in claude.ai/ChatGPT, so this is a partial win depending on which client the deployment targets. Must be built on **form mode**, not URL mode + `elicitationId`, since that correlation mechanism is removed in the 2026-07-28 RC.
- **Implementation surface:** `src/server/*-tools.ts` (tool handler adds an elicitation request before mutating), `src/orchestration/` (workflow gains an elicitation step for destructive ops), `src/transport/create-server.ts` (server capability negotiation for elicitation).

### 3. `_meta["anthropic/requiresUserInteraction"]` on `delete_chunk` (and equivalent destructive tools)
- **User-visible benefit:** Forces a Claude Code permission prompt on every call regardless of `acceptEdits`/`auto`/`bypassPermissions` mode — a hard guarantee (in that one client) that a human sees and approves destructive knowledge-graph mutations, which the standard `destructiveHint` annotation cannot guarantee (Claude Code doesn't consult it).
- **Client-support risk:** Claude Code-only (v2.1.199+), proprietary `_meta` key, no portability to other clients — but it's a single boolean flag with no downside for clients that ignore it.
- **Implementation surface:** `src/server/tool-helpers.ts` / wherever `tools/list` entries are constructed — add the `_meta` flag to the tool registration for `delete_chunk` and similarly destructive tools.

### 4. Progress notifications on bulk/long-running tool calls
- **User-visible benefit:** Confirmed to keep Claude Code from aborting a tool call after 5 minutes of silence (idle timeout only resets on progress notifications, not on elapsed time alone). Directly protects any future bulk import, embedding backfill, or multi-chunk generation call from being killed mid-flight in the one client I can verify honors it.
- **Client-support risk:** Low-medium — verified behavior in Claude Code; unverified elsewhere, but emitting progress notifications is harmless where unsupported.
- **Implementation surface:** `src/orchestration/` (long-running workflows emit progress via the MCP SDK's progress callback), `src/server/*-tools.ts` (tool handlers that wrap long orchestration calls thread the progress token through).

### 5. Resource links from search results (`search_chunks`/`search_topics`)
- **User-visible benefit:** Lets the client fetch/attach a specific chunk or topic as a first-class resource (fuzzy-@-mentionable in Claude Code, attachable in claude.ai) instead of requiring a second tool call to re-fetch content already found by search — a real ergonomic improvement in the clients where resource read/list is confirmed (Claude Code, claude.ai, Cursor, VS Code).
- **Client-support risk:** Medium — plain resource read/list is broadly confirmed, but the specific `resource_link` *content-block-in-a-tool-result* pattern (vs. top-level `resources/list`) is unverified for rendering behavior in any client I checked. Worth a small spike/manual test in your actual target client before committing.
- **Implementation surface:** `src/server/search-tools.ts` (attach `resource_link` content blocks to results), `src/server/tools.ts` (would need a matching `resources/read` handler if one doesn't already exist — confirmed via repo search that no `registerResource` calls exist today, so this is new surface, not an extension of existing code).

## 4. Not worth it yet (with reasons)

- **Sampling (`sampling/createMessage`) for server-driven question generation/grading.** This was the marquee idea in the source prompt — "move pedagogy control server-side at zero inference cost" — and the evidence says no: only VS Code confirms client-side support among 41 tracked clients; Claude Code's own reference docs never mention it; and the 2026-07-28 RC formally **deprecates** Sampling in favor of servers integrating directly with LLM provider APIs. Building this now means building for a feature the spec authors are actively walking back, for a client population that mostly doesn't implement it. If server-side pedagogy control is genuinely wanted, the RC's own recommended migration path — call an LLM provider API directly from the server — is more likely to work in more clients than waiting for sampling adoption.
- **Tasks / async long-running operations for content audits or bulk imports.** Currently experimental, zero confirmed client consumers, and mid-redesign into an extension whose shape the reference TypeScript SDK doesn't implement yet even in v2 beta. Revisit after 2026-07-28 ships and the extension has at least one client implementation.
- **Structured tool output (`outputSchema`/`structuredContent`).** No evidence any first-party client UI (Claude Desktop, claude.ai, ChatGPT, Cursor) does anything differently when it's present; the existing JSON-stringified-text pattern already works everywhere those clients are used. Low payoff for the schema-maintenance cost, especially with `outputSchema` semantics still being loosened in the RC.
- **Completions (argument autocomplete).** Zero confirmed adopters among any client checked, including the most spec-forward ones (Claude Code, VS Code). Not worth building for prompt arguments that are already simple strings.
- **Resumability / event store for Streamable HTTP.** Historically near-unused, and the 2026-07-28 RC removes SSE resumability from the spec entirely. This server has no resumability code today — leave it that way.
- **Icons.** Schema support exists since 2025-11-25 but per-client rendering is unverified everywhere I looked; cosmetic even if it works.
- **`.well-known/mcp` generic discovery.** Proposed, not shipped. This server already implements the mechanism that *is* shipped and required (OAuth PRM), so there's nothing pending here.
- **MCP Apps extension for an interactive teaching UI.** Real and officially registered, but brand new, opt-in per client, and no adoption data exists yet for any client. A multi-quarter watch item, not a current build target.
