## 1. Spec revision identified + changelog

**The current stable Model Context Protocol revision is `2025-11-25`** (confirmed live against [modelcontextprotocol.io/specification](https://modelcontextprotocol.io/specification), which now points its "Learn More" cards at `/specification/2025-11-25/*`, and against the GitHub releases list, which shows `2025-11-25` promoted from RC — `2025-11-25-RC`, Nov 15 2025 — to a stable release). This supersedes `2025-06-18`, which the recon/prompt treated as current; **it is not**. Relative to `2025-06-18`, the [`2025-11-25` changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog) adds: OpenID Connect Discovery 1.0 as an alternative to OAuth Authorization Server Metadata for AS discovery; icons metadata on tools/resources/prompts; incremental ("step-up") scope consent via `WWW-Authenticate`; formal tool-naming guidance (SEP-986); an overhauled `ElicitResult`/`EnumSchema`; URL-mode elicitation; tool-calling support inside sampling; OAuth Client ID Metadata Documents as a new (recommended) client-registration mechanism; and an experimental `tasks` utility for long-running requests. Materially for this audit, the minor changes include two load-bearing clarifications: (a) stdio servers **MAY** use stderr for *all* logging, not just errors, and (b) **"input validation errors should be returned as Tool Execution Errors rather than Protocol Errors"** (SEP-1303) — i.e. `isError: true`, not a JSON-RPC protocol error — plus an explicit new requirement that servers **MUST** respond `403 Forbidden` to invalid `Origin` headers on Streamable HTTP. These two clarifications are directly relevant to two of the biggest gaps found below.

**A much larger, not-yet-final rewrite is in `draft`** (compare: [2025-11-25...draft](https://github.com/modelcontextprotocol/specification/compare/2025-11-25...draft); a `2026-07-28 RC` label appears in the GitHub release list, though I did not independently re-verify that exact label/date — the draft's *existence and content* are confirmed directly via the changelog fetch, its target-date label is not). This is **not current** and must not be used to grade compliance today, but it is architecturally important context: the draft **removes protocol-level sessions and the `Mcp-Session-Id` header entirely**, replacing them with stateless per-request `_meta` fields and explicit server-minted handles passed as ordinary tool arguments; **removes the `initialize`/`initialized` handshake**, adding a mandatory `server/discover` RPC instead; replaces the GET/SSE `resources/subscribe` model with a single `subscriptions/listen` stream; **deprecates Roots, Sampling, and Logging outright** and reclassifies HTTP+SSE as fully deprecated; and **deprecates OAuth Dynamic Client Registration** in favor of Client ID Metadata Documents. This server's entire HTTP transport (`src/transport/http.ts`) is built around exactly the session-lifecycle machinery (`transports` map, `sessionIdentity` map, `onsessioninitialized`) that the draft removes — worth flagging as a forward-looking architectural risk, not a current-compliance failure. One silver lining: the server's `context_token` gate (`src/transport/context-token-middleware.ts`) already passes a server-minted opaque token as an ordinary tool argument rather than relying on session state, which happens to resemble the pattern the draft is moving *toward*.

## 3. Prioritized gap list

### Blockers

**B1 — Token audience (`aud`) validation is opt-in, not enforced.**
Spec: [Authorization §Token Audience Binding and Validation](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization#token-audience-binding-and-validation) + §Access Token Privilege Restriction — both explicit MUSTs.
Files: `src/transport/jwt-middleware.ts:73-76`; `src/config/resolve-auth-config.ts:3,33-42,82`.
Fix sketch: change `AUTH_AUDIENCE` from `optionalUrl()` to `requireUrl()` in `resolve-auth-config.ts` (mirroring how `AUTH_ISSUER` already fails fast via `requireEnv()`), and always pass `audience: authConfig.audience` unconditionally into `jwtVerify()`. This closes the token-confusion hole where a token minted for a different resource server (but signed by the same trusted issuer) would otherwise be accepted.

**B2 — No `Origin` header validation on Streamable HTTP.**
Spec: [Transports §Streamable HTTP Security Warning](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#streamable-http) — explicit MUST + MUST-403.
Files: `src/transport/http.ts:81,93-119`.
Fix sketch: add dedicated Origin-validation middleware ahead of the existing CORS middleware that 403s whenever `Origin` is present and not in an operator-configured allowlist, independent of what `HTTP_HOST` is bound to (the SDK's Host-header check is a different, and currently the *only*, line of defense, and it silently disengages once the host isn't localhost).

**B3 — Tool Execution Errors never set `isError: true`.**
Spec: [Tools §Error Handling](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#error-handling) (validation/business-logic errors are explicitly Tool Execution Errors) plus SEP-1303's clarification that this exists specifically so models can self-correct.
Files: `src/server/tool-helpers.ts:53-77` (`toolError()`).
Fix sketch: add `isError: true` to every `toolError()`-produced `CallToolResult`. Note the SDK's own uncaught-exception wrapper and `context-token-middleware.ts`'s hand-rolled response already set `isError:true` correctly (see Row 5) — this single change brings all three envelope-producing code paths into agreement, rather than requiring a broader rearchitecture.

### Should-fix

**S1 — No rate limiting on tool invocations.** Spec: [Tools §Security Considerations](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#security-considerations) MUST. Files: none found in `src/transport/**`. Caveat: this MUST is commonly satisfied at a reverse-proxy/API-gateway layer rather than in application code — if this deployment sits behind such a gateway with limiting already configured, this gap may be moot; verify the actual deployment topology before treating it as unmet. Fix (if not otherwise covered): add a per-subject/per-session limiter in front of `POST /mcp`.

**S2 — No scope enforcement.** Spec: general access-control MUST (row 22) + Scope Minimization guidance. Files: `src/transport/jwt-middleware.ts`, `src/transport/prm-handler.ts:8`. Fix: define app scopes (e.g. `sr:read`/`sr:write`), publish in `scopes_supported`, check `payload.scope` before mutating calls, 403 `insufficient_scope` per spec's step-up flow when missing.

**S3 — DNS-rebinding protection silently drops when `HTTP_HOST≠127.0.0.1`.** Spec: Transports §Security Warning SHOULD. Files: `src/transport/http.ts:81`. Fix: always pass an explicit `allowedHosts` (new `ALLOWED_HOSTS` env var) to `createMcpExpressApp`, independent of bind address.

**S4 — Single shared dataset, no per-user isolation.** Not an MCP-spec item, but blocks any real multi-tenant deployment and every directory listing checked in §4. Files: `src/infrastructure/db/schema.ts`. Fix: add owner/user_id columns and thread JWT `sub` through ports/adapters as a row-level scope.

**S5 — Zero adoption of `annotations`/`outputSchema` across all 45 tools.** Not a spec violation (both optional), but required for Claude Connector Directory submission (see §4) and recommended by Anthropic's own tool-authoring guidance. Files: all 16 registrars in `src/server/`. Fix: add `readOnlyHint`/`destructiveHint`/`idempotentHint`/`openWorldHint` per tool; pilot `outputSchema`+`structuredContent` on a few high-value tools (e.g. `calculate_next_review`).

### Nice-to-have

**N1 — Everything is a tool; nothing is a resource.** Official docs ([Server Concepts](https://modelcontextprotocol.io/docs/learn/server-concepts)) draw a clear line: read-only/reference data → resources (application-controlled), anything model-invoked → tools. Candidates: `get_server_info`, `get_server_workflow` (`src/server/server-info-tools.ts`, `server-workflow-tools.ts`) look like reference data currently exposed as tools.

**N2 — 45 tools is a lot for one server.** Anthropic's engineering guidance ("[Writing effective tools for AI agents](https://www.anthropic.com/engineering/writing-tools-for-agents)") explicitly recommends consolidating narrow, overlapping tools into fewer broader ones and warns that "too many tools or overlapping tools can also distract agents." See §4-adjacent best-practice findings below for consolidation examples and client-side mitigations (tool search / `defer_loading`).

**N3 — SDK is two minor versions behind.** Installed `1.27.1`; latest published is `1.29.0` (`npm view @modelcontextprotocol/sdk versions`). No known compliance defect, just staleness.

**N4 — Public `/version` exposes exact semver + build timestamp.** `src/transport/http.ts:85`, `src/shared/version.ts:25-31`. Minor info-disclosure hardening opportunity, not an MCP-spec item.

## 4. Best-practice guidance beyond the spec (delegated research, verified)

Researched and cited by a sub-agent against live sources; I reviewed the citations for plausibility and they check out against official domains (modelcontextprotocol.io, anthropic.com/engineering, platform.claude.com, code.claude.com, blog.modelcontextprotocol.io, claude.com/docs).

- **Tool naming**: spec (draft/server/tools) SHOULD-guidance is 1–128 chars, `A-Za-z0-9_-.` only, unique per server; cross-server aggregators SHOULD disambiguate via server-name prefixing. Anthropic's engineering guidance recommends namespacing by service/resource (`asana_search`, `jira_search`) and unambiguous parameter names. Claude Connector Directory review criteria hard-cap tool names at 64 characters (stricter than the spec's 128).
- **Tool count / context budget**: Anthropic's "Writing effective tools for AI agents" is explicit that too many/overlapping tools distract agents, and gives concrete consolidation examples (e.g. collapsing `list_users`+`list_events`+`create_event` into one `schedule_event` tool). Claude's MCP-connector docs recommend `defer_loading` / a "Tool search tool" for large tool sets; Claude Code doesn't hard-cap tool count but truncates descriptions at 2KB and gates on context budget.
- **Annotations**: MCP's own blog post ("Tool Annotations as Risk Vocabulary," Mar 2026) frames annotations as a risk vocabulary — omitting them defaults clients to the pessimistic assumption (non-read-only, potentially destructive, non-idempotent, open-world) — but notes "coverage is uneven" across clients. Verified, concrete consequence: Anthropic's Claude Connector Directory *requires* `title` + `readOnlyHint`/`destructiveHint` on every submitted tool and states they "determine auto-permissions in Claude." A secondary-source claim that Claude Code's permission system itself matches on annotations was checked against the official Claude Code permissions doc and could **not** be verified — Claude Code permission rules match by server/tool name only, not annotation hints. Treat "Claude Code auto-approves read-only MCP tools" as **UNVERIFIED**.
- **Resources vs. tools**: official docs state a clear preference — passive/read-only reference data → resources (application-controlled); anything requiring model judgment or side effects → tools. Adoption in the wild (including this server) skews almost entirely to tools.
- **Structured output adoption**: no Anthropic-published adoption-rate data or migration guide was found beyond the spec's own MUST/SHOULD text — marked **UNVERIFIED — no authoritative adoption/migration guidance found** for a "servers should move off text-only JSON" recommendation.
- **Claude Connector Directory checklist** (`claude.com/docs/connectors/building/review-criteria`, live-fetched): requires `title`+applicable annotation hint on every tool; tool names ≤64 chars; a single tool may not mix safe and unsafe HTTP-method semantics; descriptions must state precisely what/when; actionable (not silent) error messages; reasonably-sized responses; test credentials with a fully-populated account; public GitHub repo for the implementation; MCP Inspector exercise pre-submission. The fetched page did **not** state remote-vs-stdio, OAuth/DCR, privacy-policy, multi-tenancy, or rate-limiting requirements explicitly — those may live on adjacent, unfetched pages (see caveat in §5 below).

## 5. Directory-listing readiness checklist

Researched live against official sources by a sub-agent; citations reviewed for plausibility (all resolve to modelcontextprotocol.io, github.com/modelcontextprotocol, claude.com, platform.claude.com, support.claude.com, developers.openai.com).

### Official MCP Registry (`github.com/modelcontextprotocol/registry`)

Status: **explicitly "in preview,"** not GA ("Breaking changes or data resets may occur before general availability" — `modelcontextprotocol.io/registry/about`).

- [ ] Namespace ownership verification — reverse-DNS server name (`io.github.<user>/server` or `com.example/server`) proven via GitHub OAuth/OIDC or DNS/HTTP challenge.
- [ ] Package hosted on a **whitelisted public registry only** — npm (registry.npmjs.org), PyPI, NuGet, Docker/OCI (Docker Hub/GHCR/Quay/cloud registries), or MCPB via GitHub/GitLab releases; private registries/mirrors are rejected.
- [ ] Server must be **publicly installable or publicly reachable** — the registry explicitly rejects private/internal-only servers ("If you want to publish private servers, we recommend that you host your own private MCP registry" — `registry/about`). **This repo currently fails this bullet as-is**: `package.json:5` has `"private": true` and it is not published to any public package registry.
- [ ] `server.json` with `name`/`description`/`repository`/`version`/`packages[]`; `packages[].transport` explicitly permits `"stdio"` — **no remote-HTTP mandate** for this registry specifically.
- Moderation is reactive/permissive only (illegal content, malware, spam, non-functioning servers) — no privacy-policy, OAuth, annotation, multi-tenancy, or health-endpoint gate exists in this registry at all.

Verdict: registry listing is realistic with modest work (publish the package publicly, add `mcpName`, complete namespace verification) — no architectural blocker beyond un-flipping `"private": true`.

### Anthropic Claude Connectors Directory (`claude.com/docs/connectors/building/*`)

Three submission shapes exist: **Remote MCP servers** (HTTP-hosted), **Desktop extensions** (MCPB-packaged, for Claude Desktop, stdio-compatible), and **MCP Apps** (UI-rendering). Submission is an org-level (Team/Enterprise) admin action, not available on individual plans.

- [ ] **Published privacy policy — mandatory, immediate-reject gate** if missing or incomplete (stable public URL for Remote servers; README section + `manifest.json` `privacy_policies` array for MCPB). Directly re-verified via a live fetch of `claude.com/docs/connectors/building/submission`: *"Missing or incomplete privacy policies result in immediate rejection."* **This repo has no `PRIVACY.md`/policy of any kind — currently fails this bullet outright.**
- [ ] Remote servers must be **publicly reachable over HTTPS from Anthropic's IP ranges**; local/stdio-only servers cannot be listed as "Remote" (only via the separate MCPB Desktop-extension path). This repo does support HTTP transport (`src/transport/http.ts`) so this bullet is architecturally reachable, contingent on public hosting + fixing Gaps B1/B2 first.
- [ ] OAuth required, but **DCR is only one of three accepted options** — dynamic client registration (RFC 7591), OAuth Client ID Metadata Documents, or a static client ID issued directly by Anthropic. This repo's resource-server-only JWT setup (`src/transport/jwt-middleware.ts`) doesn't implement any client-registration mechanism itself (it delegates entirely to an external issuer) — whichever option is chosen is a property of the *authorization server* behind it, not this codebase, so this is likely satisfiable without code changes here.

### Does the MCP protocol itself require Dynamic Client Registration?

**No.** Per the Authorization spec, "Authorization servers and MCP clients **SHOULD** support... RFC 7591" — SHOULD, not MUST — and OAuth support overall is entirely OPTIONAL for MCP implementations. The `2025-11-25` revision made OAuth Client ID Metadata Documents the preferred default identity mechanism, keeping DCR only as a backward-compatibility fallback (draft revision goes further and formally deprecates DCR — see §1).
