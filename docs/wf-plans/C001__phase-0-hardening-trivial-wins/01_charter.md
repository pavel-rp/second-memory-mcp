# C001 — Phase 0: Hardening & trivial wins

**Status:** Published
**Created:** 2026-07-07  **Updated:** 2026-07-07
**Tracker:** NEU-832

**Written by:** claude-fable-5

## Problem & why now

The 2026-07-07 research synthesis (`docs/research/SYNTHESIS.md`) found that the server violates three explicit MUSTs of the current MCP spec (2025-11-25) and carries a fourth MUST-level gap, all confirmed in code:

- JWT audience validation is opt-in: `AUTH_AUDIENCE` is resolved via `optionalUrl()` (src/config/resolve-auth-config.ts:82) and only conditionally passed to `jwtVerify` (src/transport/jwt-middleware.ts:73–76), leaving a token-confusion hole (report 01 gap B1).
- No `Origin` header validation on Streamable HTTP — the `/mcp` middleware sets CORS headers but never rejects (src/transport/http.ts:93–119). The SDK's Host-header DNS-rebinding check is auto-active on the default `HTTP_HOST` of 127.0.0.1 (src/config/resolve-transport-config.ts:20) and disengages only for non-localhost binds, because `createMcpExpressApp` is called without `allowedHosts` (src/transport/http.ts:81) — with a console warning for 0.0.0.0/:: and silently for any other non-localhost host (node_modules/@modelcontextprotocol/sdk/dist/esm/server/express.js:30–47). (Report 01 gaps B2, S3.)
- Business-logic tool errors never set `isError: true`: `toolError()` (src/server/tool-helpers.ts:53–77) is the one non-conformant envelope path of three, so client models cannot self-correct (report 01 gap B3). The same file carries two dead success helpers, `toolOk` and `toolJson`, with zero call sites in `src/`.
- No rate limiting anywhere in `src/transport/**` (report 01 gap S1, a spec MUST for tool invocations).

In parallel, the pedagogy audit (report 03) graded the system C+ and identified four fixes that are one-to-few-constant changes yet are flatly supported by the literature:

- Assessment mode forces `quality = passed ? 5 : 1` (src/orchestration/teaching-workflows.ts:1226), so every correct answer registers as flawless (max ease gain) and every failure as near-blackout (Q2).
- No interval fuzz exists anywhere in the scheduler, so batch-taught chunks co-land on identical review dates forever (Q8).
- "Prerequisite mastered" means `repetitions > 0` (src/orchestration/session-workflows.ts:314) — a single lifetime success — even though the codebase already computes FSRS-style retrievability for teaching-tier selection (src/domain/algorithms/classify-chunk.ts). Report 03 calls this the cheapest, highest-leverage fix in the audit (Q9).
- The leech flag fires at `config.leechConsecutiveFailures` consecutive failures — default 3, already env-configurable via `SM_LEECH_CONSEC_FAILS` (src/config/resolve-algorithm-config.ts:57–59) — with no minimum evidence base (src/domain/algorithms/sr-calculator.ts:157), structurally far more aggressive than Anki's 8-lifetime standard, while the `leechFailureThreshold` config knob (default 6, env `SM_LEECH_FAIL_THRESHOLD`) is parsed but never read by any algorithm — dead config (Q7).

Finally, `SERVER_INSTRUCTIONS` (src/shared/instructions.ts, ~7.9 KB) is truncated at 2 KB by Claude Code and to ~512 useful chars in ChatGPT, so critical workflow rules are invisible to exactly the clients most likely to connect (report 02 §3.1).

Why now: this is Phase 0 of the unified roadmap — compliance blockers and trivial pedagogy fixes first, because they are days of work and every later phase (measurement, tenancy, directory listing, cloud) inherits them. Directory submission is explicitly blocked on B1/B2 (report 01 §4).

## Users & journeys

**Server operator (self-hosting over HTTP).** Entry: an existing `TRANSPORT=http` deployment behind Rauthy. Path: upgrades the server → startup fails fast naming the newly required env vars (`AUTH_AUDIENCE`, explicit origins in `CORS_ALLOWED_ORIGINS`, and — only when `HTTP_HOST` is a non-localhost bind — the new `ALLOWED_HOSTS` host allowlist) → sets them, optionally tuning the env-configurable rate limits → server starts. Value moment: the deployment is MCP-spec-compliant — wrong-audience tokens are rejected, forged-Origin requests get 403, abusive subjects get rate-limited — with no reverse-proxy dependency. Failure case: an operator who skips the release notes gets a startup failure with an actionable message (the same fail-fast pattern `AUTH_ISSUER` already uses), never a silently insecure server.

**AI agent (Claude Code, claude.ai, ChatGPT, …) orchestrating tools for a learner.** Entry: client connects and receives server instructions. Path: even in a client that truncates instructions at 2 KB, the agent sees the critical workflow rules (teaching loop, `submit_answer` contract, never-fabricate-scores) and can call `get_server_workflow` for full depth. Value moment: when a tool call fails a business rule, the result now carries `isError: true`, so the model recognizes the failure and self-corrects instead of treating the error envelope as data. Failure case: an agent on a non-truncating client sees restructured (but semantically complete) instructions — depth is preserved verbatim via `get_server_workflow`.

**Learner (indirect, via the agent).** Entry: existing chunks with live SR state. Path: assessment answers now register as pass→4 / fail→2 instead of 5/1; review dates carry small fuzz so batch-taught chunks spread out; a prerequisite reviewed once long ago re-enters the session when its retrievability has decayed below 0.7; a new-and-hard chunk is no longer branded a leech on its first three attempts. Value moment: scheduling reflects actual memory state instead of mechanically inflated ease and false mastery. Failure case (material, intended): previously "mastered" prerequisites re-enter sessions, so some sessions get longer immediately after the upgrade.

**Not served by this release:** multi-user tenants (single shared dataset remains), scope-based access control, learners wanting retention/calibration analytics (Phase 1), and directory-listing requirements beyond B1/B2 (annotations, privacy policy — Phase 2).

## Outcomes

The scheduling-behavior outcomes (OUT-4, OUT-5, OUT-6, OUT-8) roll out as hard cutovers: no new rollout flags or env knobs of any kind; existing `SM_*` algorithm knobs that already cover a value keep working. This no-new-configuration rule applies to OUT-4/5/6/8 only, per the 2026-07-07 rollout decision — the transport outcomes (OUT-2, OUT-9) introduce new env vars by design.

## Scope

**IN:**
- HTTP transport hardening to current-spec MUSTs: enforced token audience, Origin validation with 403 backed by a required-explicit origin allowlist, Host allowlist required for non-localhost binds (SDK localhost auto-protection retained for the default bind), in-app per-subject rate limiting (OUT-1, OUT-2, OUT-9).
- MCP tool-error conformance and dead-helper removal (OUT-3).
- Four constant-scale pedagogy corrections to live scheduling behavior: assessment quality mapping, interval fuzz, retrievability-gated prerequisite mastery, evidence-gated leech flagging (OUT-4, OUT-5, OUT-6, OUT-8).
- Instructions restructuring for truncating clients (OUT-7).
- Documentation/tests updated wherever they encode the old behavior (instructions text, schema comments, existing envelope/mapping assertions).

**OUT:**
- Scope enforcement (`sr:read`/`sr:write`), multi-tenancy/user isolation, tool annotations, privacy policy, registry/directory submission — Phase 2 (they depend on this phase but are separately shippable).
- Measurement/analytics (retention rate, calibration, `time_spent_ms` usage), correct-answer exposure after second failure — Phase 1.
- FSRS migration, lapse partial retention (the full interval-reset-on-lapse behavior stays as-is), roadblock → successive-relearning redesign, interleaving, grading-trust judge pass, tier smoothing — Phase 3. Named explicitly because they are adjacent to OUT-4/5/6/8 and must not creep in.
- Delegating rate limiting to a reverse proxy — rejected by decision; the limiter is in-app so compliance is self-contained for any deployment.
- Any session-lifecycle investment beyond what these fixes touch — the 2026-07-28 spec RC removes protocol sessions (SYNTHESIS.md corrections), which is also why OUT-9 keys on subject, not session.

## Constraints & principles

- **Hexagonal purity:** `src/domain/` is zero-I/O and never throws (project CLAUDE.md). Interval fuzz must therefore take its randomness as an injected input to the pure SR calculator, keeping tests deterministic.
- **HTTP-only blast radius for transport items:** `resolveAuthConfig` returns `null` for STDIO (src/config/resolve-auth-config.ts:78), and rate limiting/Origin checks live on the Express `/mcp` path — OUT-1/2/9 do not affect `TRANSPORT=stdio` deployments.
- **Rauthy reality:** the deployed IdP (Rauthy v0.34.3) hardcodes `aud` to the OAuth `client_id` and does not support RFC 8707 resource indicators (docs/wf-plans/NEU-63__remove-aud-claim-validation-jwt-middleware/PLAN.md). OUT-1 therefore sets `AUTH_AUDIENCE` to the client_id Rauthy actually emits. This charter **deliberately reverses NEU-63's decision** to leave `AUTH_AUDIENCE` optional; the spec phase must check whether current (2026) Rauthy has added RFC 8707 support so a proper resource URL can be used instead (decision from intake, 2026-07-07).
- **No new rollout configuration** for the scheduling-behavior changes (intake decision, 2026-07-07). Existing `SM_*` env knobs (src/config/resolve-algorithm-config.ts) that already cover a value keep working.
- **Quality scale is stable:** SM-2 quality stays 0–5 (src/shared/constants/validation.ts); OUT-4 changes which points the assessment maps to, not the scale.
- **Error envelope shape is stable:** the JSON body `{ status: 'error', error: { type, message, retryable } }` is unchanged; OUT-3 adds only the MCP-level `isError` flag.
- **Fail-open server behavior** (project CLAUDE.md): tool handlers keep returning valid MCP responses; the new 403/429 paths are transport-level rejections, not tool-layer crashes.
- **Integration tests are a ship-gate for request-blocking paths** (project CLAUDE.md): the 401/403/429 behaviors need DB-independent transport integration tests in `tests/integration/`, not stub-only unit coverage.

## Dependencies & impact

- **MCP SDK:** OUT-2 relies on `createMcpExpressApp`'s `allowedHosts` option, present in the pinned SDK version. No SDK upgrade is required by this charter.
- **Rauthy IdP:** OUT-1 depends on the `aud` value Rauthy emits (client_id today). A spec-phase check of current Rauthy for RFC 8707 decides the final `AUTH_AUDIENCE` value shape.
- **Two allowlists, two shapes:** Host validation and Origin validation are governed by different envs with different value shapes. The new `ALLOWED_HOSTS` (hostname list) feeds `createMcpExpressApp`'s SDK Host-header check and is required only for non-localhost `HTTP_HOST` binds — the default 127.0.0.1 bind keeps the SDK's automatic localhost validation (node_modules/@modelcontextprotocol/sdk/dist/esm/server/express.js:30–47), and a non-localhost bind without it fails startup instead of today's console warning. The 403 Origin check compares full origins (scheme+host+port) and reuses the existing `CORS_ALLOWED_ORIGINS` env (normalized to origins at src/config/resolve-auth-config.ts:83), which must be set to explicit origins in HTTP mode — unset or `*` fails startup — so one list governs both CORS reflection and the new 403 rejection.
- **Audience↔PRM coupling:** `AUTH_AUDIENCE` is URL-validated at startup (`optionalUrl`, src/config/resolve-auth-config.ts:33–42) and is reused as the PRM `resource` identifier (src/transport/prm-handler.ts:6) and as the base for the WWW-Authenticate `resource_metadata` URL (src/transport/jwt-middleware.ts:56–58). Setting it to a non-URL client_id would break startup parsing and PRM URL construction, so OUT-1 owns resolving this coupling (decouple the PRM/resource-metadata base from the audience, or confirm the deployed client_id is URL-shaped).
- **Existing deployments (rollout note):** OUT-1 and OUT-2 are breaking for HTTP deployments — `AUTH_AUDIENCE` becomes required, and `CORS_ALLOWED_ORIGINS` must be set to explicit origins (unset or `*` fails startup; decision 2026-07-07). `ALLOWED_HOSTS` is required only for non-localhost `HTTP_HOST` binds — the default 127.0.0.1 bind keeps the SDK's automatic localhost Host validation, so localhost-bound deployments are not broken by the host allowlist. Release notes must name the new/newly-required env vars; startup errors must be self-explanatory. STDIO deployments are unaffected.
- **Live learner data:** OUT-4/5/6/8 change future scheduling of existing chunks (ease trajectories, review dates, prerequisite session composition, leech flagging). No data migration; stored SR state is not rewritten.
- **Existing behavior encoded elsewhere:** the 5/1 mapping is documented in `SERVER_INSTRUCTIONS` (src/shared/instructions.ts:33) and a schema comment (src/infrastructure/db/schema.ts:208); `get_server_workflow` serves `SERVER_INSTRUCTIONS` verbatim, so OUT-7's restructuring automatically propagates there. Existing tests asserting 5/1, missing `isError`, or unfuzzed intervals must be updated in the same change.
- **Leech data availability:** chunks carry `repetitions` (reset to 0 on failure) and `consecutiveFailures` only — no lifetime-attempt counter exists in `learning_chunks` (src/infrastructure/db/schema.ts). A minimum-total-attempts gate needs a derived count (e.g. from `session_question_attempts`) or a new counter; the spec phase picks the mechanism.
