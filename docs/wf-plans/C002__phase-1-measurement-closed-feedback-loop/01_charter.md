# C002 — Phase 1: Measurement — closed feedback loop

**Written by:** claude-fable-5

## Problem & why now

The 2026-07-07 pedagogy audit (`docs/research/results/03-pedagogy-evidence-audit.md`, executive finding #3 and Q13) found that the system records rich attempt-level evidence but computes none of the standard SRS health metrics from it — it has **no closed loop** and cannot tell whether it is working:

- Every scored answer persists pass/fail, quality, and latency: `session_question_attempts` carries `passed`, `quality`, `agent_quality`, `time_spent_ms` (NOT NULL), and `created_at` (src/infrastructure/db/schema.ts:197–228). Yet the only analytics that exist — `analytics_daily` / `analytics_window` (src/server/analytics-tools.ts) — aggregate quality-by-date KPIs from a join over those attempts (src/adapters/drizzle/review-persistence-adapter.ts:61–101). No true retention rate (Anki ships this as a first-class "True Retention" table), no calibration check (RMSE-bins/log-loss, the FSRS benchmark's standard axis) — no code in `src/` computes either.
- Worse, the raw material for "pass rate at due time" is not fully persisted: `learning_chunks` holds only the *current* SR state (`next_review_at`, `ease_factor`, `repetitions`, `interval_days` — src/infrastructure/db/schema.ts:59–65), mutated on each review. Attempts carry no snapshot of what the interval, overdueness, or predicted recall were at answer time; only the session-level `teaching_approach` tier is snapshotted (src/infrastructure/db/schema.ts:137).
- The moment the evidence says matters most is silently dropped: after a second failed attempt, `submit_answer` marks the question answered and returns `recorded` with nothing else (src/orchestration/teaching-workflows.ts:1124–1127). Pashler et al. 2005 found supplying the correct answer after an incorrect response increased final retention by 494% (report 03 Q4) — the system does nothing at exactly that moment.
- `time_spent_ms` is collected on every attempt but never analyzed as a fatigue signal. Session guidance instead runs on fixed clocks: the 90-minute `timeThresholdMs` and 2-hour `maxTimeMs` (src/domain/config/algorithm-defaults.ts:30–35) drive `session_status`'s continue/complete/break recommendation (src/domain/services/session-analyzer.ts:159–164). Report 03 Q12 found no evidence anchoring either number, and the strongest evidence favors periodic micro-breaks over a single cutoff.
- Dead pedagogy surface pretends to sophistication the system doesn't have: `calculateItemCognitiveLoad` (src/domain/services/cognitive-load.ts) has zero call sites, and the `sessionComposition` config block (maxNew caps, easy-medium-hard `interleaveStrategy`) is typed, defaulted, and parsed from six `SM_REC_*` env vars (src/config/resolve-algorithm-config.ts:114–140) but read by nothing. Report 03 Q13 #6: an uninvoked model is itself a measurement gap.

Why now: this is the **enabling phase** of the 2026-07-07 roadmap (`docs/research/SYNTHESIS.md`, Phase 1). Phase 0 (NEU-832, sub-tasks NEU-833–841) just changed live scheduling behavior — quality mapping, interval fuzz, prerequisite gating, leech flagging — and none of those changes can currently be shown to help or hurt. The Phase 3 FSRS migration cannot be validated without a retention/calibration baseline. Strategically (report 04 / SYNTHESIS monetization), these metrics are the future paid surface — the consumer "is this working for me" screen and the B2B dashboard — so their data shapes are designed for that reuse, while all UI stays out of scope.

## Users & journeys

**System owner / operator (validating the scheduler).** Entry: months of accumulated review history on a post-Phase-0 scheduler. Path: calls the new `analytics_health` tool → receives true retention (overall and by teaching tier / interval band) and a calibration comparison of predicted vs. observed recall, each with its sample coverage. Value moment: for the first time, an answer to "do the scheduler's assumptions match observed recall?" — the baseline every later change (including FSRS) is judged against. Failure case: too few reviews carry scheduling snapshots yet → the tool returns honest low-coverage figures with sample sizes, never authoritative-looking aggregates over thin data.

**Learner (via the AI agent) failing a question twice.** Entry: second failed attempt on a session question. Path: `submit_answer` returns `recorded` as today, now with an additive correct-answer block (chunk-derived answer/explanation material plus a directive) → the agent presents the correct answer before moving on. Value moment: corrective feedback at the moment with the largest confirmed effect size in the audit, instead of a silent recording. Resolution: scheduling proceeds unchanged — light-touch exposure, not a forced restudy. Failure case: the chunk has no stored `content` → the block degrades to the directive plus whatever material exists (title, condensed summary); recording the attempt is never blocked.

**Learner in a long session (via the agent).** Entry: a session where per-attempt latency is rising and quality falling. Path: the server computes the per-session fatigue trend from persisted attempts and injects a break advisory block into `teach_next`/`submit_answer` responses when it fires → the agent proposes a micro-break. Value moment: a measured, personal stopping signal replaces the unvalidated fixed 90-minute clock, with no polling dependency. Resolution: learner breaks and resumes; advisories recur while the signal persists. Failure case: the agent ignores the advisory — it is advisory-only and repeats on subsequent responses; the teaching flow is never interrupted by the server.

**Not served by this release:** anyone wanting a dashboard or UI (Phase 2+ consumes these data shapes); multi-user tenants (metrics are computed over the single shared dataset until Phase 2 tenancy); learners wanting forgetting-curve fits or lapse-rate/time-to-relearn analytics (report 03 Q13 #3–4 — deliberately excluded from the Phase 1 table).

## Constraints & principles

- **Hexagonal purity (non-negotiable, project CLAUDE.md):** retention, calibration, and fatigue-trend computations are pure domain functions — zero I/O, never throw; attempt/snapshot data reaches them through ports/adapters.
- **Hard cutover, no new rollout flags** — the established Phase 0 precedent for behavior changes (intake decision, applies feature-wide).
- **Additive response evolution:** `submit_answer` and `teach_next` gain optional blocks only; existing fields, actions, and the retry/recorded state machine are unchanged. Additive = hard-cutover safe (intake clarification).
- **Integration tests are a ship-gate for DB-mutating paths** (project CLAUDE.md): the OUT-2 capture path and its migration require DB-backed tests in `tests/integration/`, not stub-only coverage.
- **Drizzle migration discipline:** `drizzle/meta/_journal.json` `when` timestamps must stay monotonically increasing (project CLAUDE.md) — OUT-2's additive migration follows it.
- **Naming boundary:** snake_case in MCP tool schemas, camelCase internally, converted in `src/server/*-tools.ts` (project CLAUDE.md); `analytics_health` follows the existing registration and `toolData`/`toolError` envelope conventions (including Phase 0's `isError` conformance).
- **One new tool only:** `analytics_health` is the single addition — a deliberate +1 against Phase 2's tool-consolidation goal, chosen because lifetime/cohort health metrics are a different shape from the date-window KPI tools (intake decision).
- **Dashboard-contract mindset:** the `analytics_health` output shape is designed for reuse by the future consumer screen and B2B dashboard (SYNTHESIS monetization note) — stable field names, breakdowns, and coverage figures — without building any UI.
- **Fail-open server behavior** (project CLAUDE.md): metric computation failures return valid MCP error envelopes; advisory and correct-answer block injection is best-effort and must never fail an otherwise-successful teaching call.
- **Honest metrics:** every aggregate carries its sample size/coverage — a direct consequence of the audit's finding that unvalidated numbers presented as authoritative are the existing failure mode (report 03 Q12).

## Dependencies & impact

- **Phase 0 in-flight overlap (the reason OUT-1 exists):** NEU-837 (assessment quality mapping) modifies the same `submit_answer`/teaching-workflows path OUT-5 touches; NEU-839 (leech evidence gate + dead-config elimination, whose verification includes an AlgorithmConfig consumption audit) may already have removed parts of OUT-7's targets. This charter may execute well after it is written; OUT-1 re-verifies before anything lands.
- **Data available today:** `session_question_attempts` provides `passed`, nullable `quality` (null on historical rows), `agent_quality`, `question_type`, `time_spent_ms`, `created_at`, `attempt_number` (1|2); `session_chunks.teaching_approach` snapshots the tier per session. **Data missing today:** no per-attempt scheduling snapshot — OUT-2 adds it additively.
- **Historical reviews:** attempts predating OUT-2 lack scheduling snapshots. Metrics compute over snapshot-bearing rows and report coverage; whether older history is approximately reconstructed by deterministic replay of the SM-2 sequence is a spec-phase decision (assumption #6). Phase 3's FSRS backfill (SYNTHESIS 3.1) needs replay machinery regardless — nothing in this charter forecloses it.
- **The implicit prediction model:** `classifyChunk`'s FSRS power-law retrievability (src/domain/algorithms/classify-chunk.ts) is the system's only predicted-recall estimate; OUT-4 calibrates it as-is. Fresh/no-interval chunks score R = 1.0 (classify-chunk.ts:45–47) — OUT-3 excludes that band from the retention headline (reported separately, assumption #14); for calibration the band must still be handled explicitly (its own bin or exclusion, a spec-phase choice) rather than let it distort the comparison.
- **Agent-reported timing:** `time_spent_ms` arrives as a `submit_answer` input from the agent; the fatigue signal inherits its fidelity (see Risks).
- **Correct-answer material:** the server holds chunk `content` and `condensed_summary` (both nullable, src/infrastructure/db/schema.ts:69,74) but no per-question canonical answer — OUT-5's block is chunk-material-plus-directive (assumption #8).
- **Existing behavior affected:** `session_status`'s **break**-recommendation semantics change with OUT-6 (the completion branches, including `qualityMet && timeMet` → 'complete', survive — assumption #13); prose documenting it (src/shared/instructions.ts:49, src/shared/prompts/prompt-pack.ts:570) must be updated in the same change, as must existing tests asserting the current `submit_answer` response shape.
- **Rollout:** hard cutover; one additive DB migration; no stored rows rewritten; release notes document the new tool, the two new response blocks, and the changed break semantics.

| Risk | Severity | Mitigation |

| Deleting `sessionComposition`/cognitive-load breaks an unseen consumer | Low | Grep/type-check show zero consumers today; OUT-1 re-verifies at execution time; type-check + zero-reference grep gate the deletion |

| Fatigue-trend computation adds per-call DB cost to the hot teaching path (`teach_next`/`submit_answer`) | Low | The trend must compute from attempt data the teaching workflow already loads, or at most one additional indexed per-session query over `session_question_attempts`; never a cross-session scan |
