# QA Rules — Second Memory MCP

Generated by `/wf:qa-init` on 2026-05-26. Edit freely — this is a living document.

## Project Profile

- **Type:** MCP server (AI-powered spaced-repetition learning)
- **Stack:** TypeScript, Node.js 20+, PostgreSQL via Drizzle ORM, MCP SDK, Vitest, pnpm
- **Architecture:** Hexagonal (ports/adapters). STDIO transport deprecated; HTTP (Streamable HTTP/SSE) is primary.
- **Critical areas:** End-to-end learning flows (content generation, teaching, session bootstrap/dispatch), data integrity, auth + transport
- **Compliance:** None

---

## Mandatory Test Scenarios

These scenarios must be included by `/wf:qa-gen` for every feature, in addition to spec-derived tests.

- **Malformed & edge-case input:** Every MCP tool must be tested with empty strings, missing required fields, Unicode/special characters, and excessively long payloads.
  - Applies to: all MCP tools
  - Priority: P1

- **DB state edge cases:** Test against empty topics (no chunks), zero reviews, orphaned sessions, already-completed reviews, and chunks with no review history.
  - Applies to: all workflows that read or write DB state
  - Priority: P1

- **Non-deterministic agent behavior:** The AI agents consuming this server are highly non-deterministic. Test that the server enforces predictable behavior regardless of the order, timing, or content of agent requests. Verify guardrails, validations, and error messages steer agents back on track.
  - Applies to: teaching flow, session management, submit_answer, any tool that accepts agent-generated input
  - Priority: P0

- **Session state machine:** Every session flow must verify valid state transitions (created -> active -> completed). Verify that invalid transitions are rejected with clear errors, not silently ignored.
  - Applies to: session lifecycle tools (create_session, start_learning, complete_session, submit_answer, teach_next)
  - Priority: P0

- **MCP response format:** All tools must return valid MCP responses via toolOk/toolError. No tool may crash, return raw exceptions, or produce malformed JSON. Errors must be user-facing and actionable.
  - Applies to: all MCP tools
  - Priority: P0

## Severity Rules

These override the default priority assignment in `/wf:qa-gen`.

- **Main learning flows** (start_learning, teach_next, submit_answer, complete_session, what_to_learn_today) -> always P0
  - Rationale: If the core learn loop breaks, the server has no value.

- **Data integrity** (DB migrations, review persistence, chunk/topic CRUD, session persistence) -> always P0
  - Rationale: Data loss or corruption is unrecoverable for the learner's progress.

- **Auth + transport** (JWT validation, context tokens, HTTP transport, MCP protocol compliance) -> always P0
  - Rationale: Connection or auth failure means complete service outage.

## Acceptance Criteria

- **Minimum pass rate:** 95%
- **P0 gate:** All P0 must pass (strict) — a single P0 failure fails the entire run regardless of overall rate
- **Evidence requirement:** Required for all failures (logs, MCP responses, DB state, browser screenshots as applicable)

## Custom Rules

- **Broken-semantics resilience:** When testing any tool that accepts agent-generated text (answers, feedback, topic descriptions), include adversarial inputs: off-topic responses, copy-pasted prompts, empty/whitespace-only text, extremely verbose responses, responses in the wrong language. The server must handle all gracefully.
- **Idempotency of read operations:** Tools that fetch state (get_session, get_chunk_content, list_learning_items) must be safe to call multiple times in rapid succession without side effects or state changes.
- **Error message quality:** Failed operations must return error messages that an AI agent can parse and act on. Verify error messages contain: what went wrong, what was expected, and what the agent should do next.

## Automation

Instructions for `/wf:qa-auto` to execute test steps autonomously. The agent reads this section verbatim and uses it to translate test actions into tool calls.

- **Interaction model:** Browser automation — the agent navigates claude.ai and simulates real-user interactions with the Second Memory MCP server through the Claude interface.
- **Browser tools:** Use Chrome MCP (console Claude Code) or full Chrome automation (desktop Claude Code) for browser control.
- **Base URL:** https://claude.ai (agent must be pre-authenticated)
- **Start command:** Assume the MCP server is already running and connected to the Claude session.
- **Ready check:** Verify the server is connected by calling `get_server_info` via the Claude interface. If it returns server metadata, the server is ready.
- **Stop command:** None — server lifecycle is managed externally.

### Tool Instructions

- **Authentication:** The user provides claude.ai auth (session cookies or login). The agent must not store or log credentials.
- **Exercising MCP tools:** Navigate to a Claude conversation, invoke Second Memory tools by instructing Claude to call them (e.g., "Call start_learning" or "Call create_topic_with_chunks with..."). Parse Claude's responses for MCP tool output.
- **Database verification:** Use the DB Access MCP (`mcp__dbhub__execute_sql`, `mcp__dbhub__search_objects`) to query Postgres directly and verify persistence. Example: after `create_topic_with_chunks`, run `SELECT * FROM topics WHERE title = '...'` to confirm the topic was persisted.
- **Log verification:** Check server stderr/pino logs for unexpected errors, warnings, or stack traces that indicate silent failures even when the MCP response looks successful.
- **Seed data:** If the test requires a clean state, the agent can create fresh topics/chunks via `create_topic_with_chunks`. Avoid modifying existing user data — always create new test content with clearly-marked test titles (e.g., "[QA-TEST] ...").
- **Session flow testing:** To test the full learning loop: call `what_to_learn_today` -> `start_learning` -> interact via `submit_answer` with various quality responses -> `teach_next` until complete -> `complete_session`. Verify each step returns the expected `data.action`.
- **Cleanup:** After test completion, note any test data created but do not delete it unless the test plan explicitly requires cleanup.
