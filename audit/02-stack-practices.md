# Stack Best-Practices Audit

Audit date: 2026-02-23
Codebase: `second-memory-learning` (MCP server — TypeScript / Node >=20 (CI: 20.x; audited on 22.x) / SQLite)

Severity scale: **Critical** > **High** > **Medium** > **Low** > **Info**

## 1. FRAMEWORK PATTERNS

### 1.1 MCP SDK (v1.18.2)

### 1.2 TypeScript

| #   | Finding                                                                                                                                                                                                                                                                                                                                                                                                                         | Severity | Location          |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ----------------- |
| F-5 | **`moduleResolution: "Node"` with ES module project** — `tsconfig.json` sets `moduleResolution: "Node"`, which is the legacy CommonJS resolution algorithm. For `"module": "ES2022"` projects, `"Node16"` or `"NodeNext"` or `"Bundler"` is the correct setting. The legacy mode doesn't understand `package.json` `"exports"` fields, which can cause incorrect type resolution for ESM-only packages (including the MCP SDK). | High     | `tsconfig.json:6` |
| F-6 | **`--max-warnings 100` in lint script** — The ESLint script allows up to 100 warnings before failing. This is unusually permissive and effectively disables warning enforcement. Best practice is `--max-warnings 0` once the backlog is cleared.                                                                                                                                                                               | Low      | `package.json:14` |
| F-7 | **Strict mode enabled correctly** — `strict: true`, `forceConsistentCasingInFileNames: true`, `skipLibCheck: true` is a solid baseline. No `any` types found in source code (only `z.any()` in Zod schemas).                                                                                                                                                                                                                    | Info     | `tsconfig.json`   |

### 1.3 Drizzle ORM

| #    | Finding                                                                                                                                                                                                                                                                                                                                                                                                     | Severity | Location                   |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | -------------------------- |
| F-8  | **Manual DDL migration instead of Drizzle Kit migrations** — `migrate.ts` runs raw `CREATE TABLE IF NOT EXISTS` + `ALTER TABLE` statements manually. Drizzle Kit provides `drizzle-kit generate` and `drizzle-kit migrate` for versioned, repeatable migrations. The manual approach duplicates the schema definition (once in `schema.ts`, once in `migrate.ts`), risks drift, and lacks rollback support. | High     | `src/db/migrate.ts:33-104` |
| F-9  | **`clearAllTables()` references dropped tables** — `client.ts:63-70` deletes from `friction_metrics`, `review_schedule`, `session_logs`, and `performance_analytics`, but `migrate.ts` drops these legacy tables at startup. After migration, these `DELETE` statements will fail silently or throw.                                                                                                        | Medium   | `src/db/client.ts:60-71`   |
| F-10 | **Drizzle query results used correctly** — `.get()` for single row, `.all()` for collections, `.run()` for mutations with `.changes` inspection. The `withTx` helper properly wraps transactions.                                                                                                                                                                                                           | Info     | —                          |

New developers must read `config/algorithm.ts` to discover all tunable parameters.                                      | Medium                                                                                                                                                                                     | `src/config/algorithm.ts`                   |

## 4. ASYNC & CONCURRENCY

| #   | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Severity | Location                                                                             |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------ |
| A-1 | **Sync better-sqlite3 calls wrapped in `async` functions** — All service functions (`createSession`, `getChunk`, `updateChunk`, etc.) are declared `async` but use synchronous `better-sqlite3` calls (`.run()`, `.get()`, `.all()`). This means every `await` on these functions creates unnecessary microtask overhead. The `async` declarations are technically harmless but misleading — they suggest non-blocking I/O when the operations actually block the event loop. | Medium   | `src/services/sessions.ts`, `src/services/chunks.ts`, `src/services/topics.ts`, etc. |
| A-2 | **No unhandled rejection / uncaught exception handlers** — The MCP server bootstrap does `bootstrap().catch(...)` with `process.exit(1)`, but there are no global `unhandledRejection` or `uncaughtException` handlers. An unhandled promise rejection in a tool handler could crash the server silently. The MCP SDK may handle this internally, but explicit handlers would be safer.                                                                                       | Medium   | `src/server/main.ts:229-232`                                                         |
| A-3 | **`batchCreateSessionChunks` inserts rows sequentially without transaction** — `sessions.ts:387-403` inserts session chunks in a `for` loop without wrapping in a transaction. If an insert fails midway, the session ends up with partial chunk data. Compare with `persistBatchSessionChunkOperations`, which correctly uses `withTx`.                                                                                                                                      | High     | `src/services/sessions.ts:384-404`                                                   |
| A-4 | **`getHistoricalFeedbackForChunks` fetches ALL completed sessions** — The query at `sessions.ts:450-455` selects all completed sessions ordered by end time, then filters in JavaScript. For a database with many completed sessions, this loads the entire session history into memory. Should use SQL `WHERE` with chunk ID filtering or at minimum a `LIMIT`.                                                                                                              | Medium   | `src/services/sessions.ts:450-455`                                                   |
| A-5 | **Timeout in `PrerequisiteValidator.withTimeout` leaks timers** — The `setTimeout` in the timeout promise is never cleared when the actual operation completes first, leading to dangling timer handles. Should use `AbortController` or clear the timeout on resolution.                                                                                                                                                                                                     | Low      | `src/tools/prerequisite-validator.ts:98-104`                                         |
| A-6 | **No graceful shutdown** — There's no `SIGTERM`/`SIGINT` handler to close the SQLite database connection or the MCP transport cleanly. For an MCP stdio server this is low-risk since the parent process manages lifecycle, but `db.close()` is only called in `resetDatabase()` (a test utility).                                                                                                                                                                            | Low      | `src/server/main.ts`, `src/db/client.ts`                                             |
| A-7 | **`bulkInsert` helper is properly chunked** — `operations.ts:30-39` splits large inserts into configurable chunk sizes (default 500). This prevents SQLite statement size limits from being exceeded.                                                                                                                                                                                                                                                                         | Info     | `src/db/operations.ts:30-39`                                                         |

## 5. SECURITY

| #   | Finding                                                                                                                                                                                                                                                                                                                                                                                          | Severity | Location                                                                |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- | ----------------------------------------------------------------------- |
| S-1 | **Node inspector enabled in production script** — (Same as C-4) `--inspect=9229` in `start:stdio` exposes a Chrome DevTools Protocol endpoint. If the MCP server is reachable on a network, this allows arbitrary code execution. Remove the flag or gate it behind an env var.                                                                                                                  | Critical | `package.json:11`                                                       |
| S-2 | **SQL injection mitigated by Drizzle ORM** — All database queries use Drizzle's parameterized query builder, which prevents SQL injection. The raw `sql` template tag in `chunks.ts:436-443` (for JSON query) is also safe because it uses tagged template interpolation, which Drizzle parameterizes. Manual `db.exec()` calls in `migrate.ts` use static DDL only.                             | Info     | —                                                                       |
| S-3 | **No authentication or authorization on MCP tools** — The MCP server exposes all tools without any auth mechanism. This is standard for local MCP servers communicating via stdio with a trusted client (Claude Desktop), but if the transport were ever changed to HTTP/SSE, all tools would be publicly accessible.                                                                            | Low      | `src/server/main.ts`                                                    |
| S-4 | **Session feedback logged verbatim** — `session-management-tools.ts:493` logs user-provided feedback directly: `logger.info('Completed session ... with feedback: ${feedback}')`. If feedback contains sensitive information, it will appear in logs. The logger outputs to stderr, which is appropriate for MCP, but feedback could leak to log aggregators.                                    | Low      | `src/server/session-management-tools.ts:493`                            |
| S-5 | **Database path traversal partially mitigated** — `SM_DB_PATH` is resolved via `path.resolve()` which normalizes `..` segments, but there's no validation that the resolved path is within an expected directory. An attacker who controls the env var could point the database at any writable location. For a local-first app this is acceptable since env vars are trusted, but worth noting. | Low      | `src/db/client.ts:10-11`                                                |
| S-6 | **No input size limits on search queries** — `searchLearningContent` accepts any-length `query` string. While the `LIKE` clause via Drizzle is parameterized (safe from injection), extremely long search strings could cause performance degradation in the SQLite `LIKE` operation. The result `limit` is capped at 50, which is good.                                                         | Low      | `src/services/search.ts:150`                                            |
| S-7 | **Content size validation is implemented** — `VALIDATION_CONSTANTS` enforces `MAX_CONTENT_SIZE: 50000` and `MAX_SUMMARY_SIZE: 5000`. The `TopicCreationService` validates these limits. This prevents unbounded data storage.                                                                                                                                                                    | Info     | `src/constants/validation.ts`, `src/services/topic-creation.ts:330,341` |
| S-8 | **Foreign keys enabled and ON DELETE cascades configured** — `PRAGMA foreign_keys = ON` is set in `applyPragmas()`. Schema uses appropriate `ON DELETE CASCADE` and `ON DELETE SET NULL`. This prevents orphaned records.                                                                                                                                                                        | Info     | `src/db/client.ts:34`, `src/db/schema.ts`                               |

## Top Recommendations (Ordered by Impact)

1. **Remove `--inspect=9229` from `start:stdio`** (S-1/C-4) — Immediate security fix.
2. **Replace `z.any()` with typed schemas** (F-1) — Define proper Zod schemas for `SessionInput` and learning items.
3. **Switch `moduleResolution` to `"Node16"` or `"NodeNext"`** (F-5) — Align TypeScript config with ESM project.
4. **Adopt Drizzle Kit migrations** (F-8) — Stop duplicating schema in DDL strings; use generated migrations.
5. **Wrap `batchCreateSessionChunks` in a transaction** (A-3) — Prevent partial session chunk creation.
6. **Add `.env.example` with all `SM_*` variables documented** (C-1) — Developer experience improvement.
7. **Validate enum env vars (`interleaveStrategy`, `verbosity`)** (C-3) — Prevent silent misconfiguration.
8. **Optimize `getHistoricalFeedbackForChunks` query** (A-4) — Filter in SQL, not in JS.
